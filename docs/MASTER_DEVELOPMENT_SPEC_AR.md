## 2. فلسفة التطبيق

التطبيق مدير تنفيذي رقمي لمتابعة العمل اليومي: العملاء، الطلبات، التصنيع، المنتجات والمخزون، الفواتير والتحصيلات، المصروفات، الخزينة، والتنبيهات. يجب أن تكون المعلومات المهمة سهلة الوصول، وألا تتحول المنظومة إلى برنامج محاسبي أو ERP معقد.

## 3. المتطلبات العامة والأداء

1. حفظ مؤقت تلقائي للبيانات أثناء إدخال طلب أو منتج، واستعادتها إذا أُغلق التطبيق أو خرج المستخدم بالخطأ.
2. منع تكرار العمليات عند الضغط المتكرر أو بطء الاستجابة، خصوصاً إنشاء الطلب/المنتج والتحصيل وحركات الخزينة. إظهار حالة «جارٍ الحفظ» وتعطيل الإجراء حتى اكتماله، مع تنفيذ العملية مرة واحدة فقط.
3. سجل نشاط بسيط لأهم العمليات: إضافة منتج، تعديل سعر، إنشاء طلب، حذف أو إلغاء بيانات، والتعديلات المالية؛ مع التاريخ والوقت.
4. تحسين سرعة فتح الصفحات والتنقل، تحميل البيانات عند الحاجة، تجنب إعادة تحميل الصفحة بالكامل بعد كل تعديل، والاستفادة من البيانات المحملة سابقاً دون التضحية بدقتها.
5. الحفاظ على وظائف المشروع الحالية والتوافق مع بنية Capacitor الحالية.

## 4. الأمان والصلاحيات

- تكلفة التصنيع والأرباح بيانات داخلية لا تظهر للعملاء أو في مستنداتهم أو الكتالوجات أو المشاركات.
- كل فئة عميل ترى أسعارها المخصصة فقط.
- العمليات الإدارية الحساسة لصاحب التطبيق فقط.
- صلاحيات صاحب التطبيق فقط: إلغاء إيصالات التحصيل، تعديل/إلغاء المصروفات وحركات الخزينة، وتصحيح إقفالات الأيام السابقة والرصيد الافتتاحي.
- منع تسرب أي بيانات داخلية عند إنشاء الفواتير أو الكتالوجات أو ملفات PDF أو المشاركة عبر واتساب.
- الاحتفاظ بسجل واضح للتعديلات والإلغاءات وأسبابها، وعدم تغيير السجلات التاريخية بصمت.

## 5. الطلبات ودورة العمل

### 5.1 صفحة الطلبات
ثلاثة أقسام في شريط تنقل أفقي أعلى محتوى الصفحة، مع بقاء الهيدر الرئيسي الثابت:
- نظرة عامة.
- طلب جديد.
- سجل الطلبات.

ينقسم سجل الطلبات إلى:
- الطلبات المفتوحة.
- الأرشيف، ويضم الطلبات المكتملة والمغلقة.

مع الإبقاء على البحث والترتيب وفلاتر التاريخ.

### 5.2 تفاصيل الطلب
تبويبات:
- الملخص.
- المنتجات والتصنيع.
- التحصيل والفواتير.
- الشحن والمتابعة.

### 5.3 دورة الحالة
جديد ← قيد التصنيع ← جاهز للشحن ← تم الشحن ← مكتمل.

- لا ينتقل الطلب للأرشيف بمجرد الشحن؛ ينتقل بعد تأكيد التسليم.
- الإغلاق حالة استثنائية مع تسجيل السبب.
- تسجيل تاريخ ووقت كل تغيير حالة.
- لا صرف مخزون أو خامات أو تحصيل تلقائي لمجرد تغيير الحالة.
- لا يُعتبر إصدار الفاتورة تحصيلاً.

## 6. التصنيع والمخزون

- إدارة مخزون المنتجات النهائية فقط حالياً؛ لا توجد إدارة خامات.
- تسجيل الإنتاج الفعلي بعد تأكيد الكمية المنتجة.
- توزيع الإنتاج تلقائياً على الطلبات حسب الأقدم أولاً، مع السماح بالتعديل اليدوي قبل التأكيد.
- حجز المخزون عند حفظ الطلب وتأكيد إنشائه، وليس عند فتح نموذج الطلب.
- السماح بإنشاء الطلب عند نقص المخزون؛ يحجز المتاح ويسجل الباقي كمطلوب تصنيعه.
- عند الشحن الفعلي يتحول المحجوز إلى صرف مخزون.
- عند إغلاق الطلب تُحرر الكميات المحجوزة بعد التأكيد، مع الاحتفاظ بالمنتجات المصنعة فعلياً في المخزون.
- عدم حذف أو تعديل حركات المخزون السابقة.

## 7. العملاء والتحصيل والفواتير

### 7.1 التحصيل
- دعم المقدم والدفعات المتعددة والتسوية النهائية.
- حساب إجمالي المدفوع والمتبقي تلقائياً.
- سجل مستقل لكل دفعة مرتبط بالعميل والطلب والفاتورة.
- منع تسجيل الدفعة مرتين، ومنع التحصيل الزائد عن المتبقي.
- فصل الحالة المالية عن التصنيع والشحن.
- طرق الدفع: نقدي، تحويل بنكي، محفظة إلكترونية، وطرق أخرى قابلة للإضافة.
- تقارير التحصيل والمتبقي حسب اليوم والفترة وطريقة الدفع.
- موعد استحقاق اختياري لكل دفعة.

### 7.2 الفواتير والإيصالات
- فاتورة أساسية واحدة لكل طلب، وإيصال مستقل لكل دفعة.
- إعادة الطباعة لا تنشئ فاتورة أو إيصالاً جديداً ولا تغير الرقم المسلسل.
- إيصال التحصيل يوضح المبلغ المستلم والمتبقي بعد الدفع.
- رقم مسلسل فريد مستقل لكل إيصال تحصيل، ويظل محفوظاً حتى إذا ألغي.
- إلغاء الإيصال يتطلب تأكيداً وسبباً؛ يحتفظ التطبيق بالسجل الأصلي بحالة «ملغي».
- تسجيل تاريخ التعديل والقيم القديمة والجديدة وسبب التعديل.
- لا يسمح بتخفيض الفاتورة إلى أقل من إجمالي المدفوع.
- لا تظهر تكلفة التصنيع أو الأرباح في مستندات العملاء.
- لا يوجد نظام مرتجعات أو استبدال؛ لا تضف المرتجعات أو فروق الاستبدال في الفاتورة أو واتساب أو الحسابات.

### 7.3 كشف حساب العميل
داخل صفحة تفاصيل العميل، دون صفحة مستقلة، ويعرض إجمالي الطلبات والخصومات والمبالغ المحصلة والمتبقية والطلبات ودفعات التحصيل وأرقام الإيصالات وتواريخ وطرق الدفع. يدعم فلترة زمنية وطباعة/مشاركة PDF عبر واتساب، دون تكلفة التصنيع أو الأرباح.

### 7.4 تنبيهات التحصيل في الرئيسية
- «مستحق»: يوجد رصيد متبقٍ.
- «موعد قريب»: اقترب موعد التسليم مع وجود مبلغ مستحق.
- «متأخر»: تجاوز موعد التسليم مع وجود مبلغ مستحق.
يعرض التنبيه اسم العميل ورقم الطلب والمبلغ المتبقي، ويفتح تفاصيل الطلب عند الضغط. لا ترسل رسائل أو إشعارات تلقائية للعميل.

## 8. المصروفات والحركة المالية

- سجل مصروفات تشغيلية بسيط: المبلغ، نوع المصروف، التاريخ، ملاحظات اختيارية، طريقة الدفع، وصورة إيصال اختيارية.
- تقارير إجمالي المصروفات اليومية والفترية.
- تعديل المصروفات مع حفظ القيم القديمة والجديدة والسبب.
- إلغاء المصروفات بتأكيد وسبب، مع الاحتفاظ بالسجل كملغي.
- تقرير حركة مالية يومية وفترية للتحصيلات والمصروفات وصافي الحركة، مع التفاصيل حسب طريقة الدفع ونوع المصروف.
- لا تخلط المصروفات بتحصيلات العملاء، ولا تحول القسم إلى نظام محاسبة تكاليف أو أرباح معقد.

## 9. قسم الخزينة — مواصفات معتمدة ومغلقة للمناقشة حالياً

قسم رئيسي مستقل في القائمة، وله أربعة تبويبات: نظرة عامة، حركة الخزينة، إقفال اليوم، التقارير. تمت مراجعة متطلباته وإغلاق مناقشته مؤقتاً؛ لا تفتح مقترحات جديدة فيه دون طلب المستخدم.

### 9.1 صلاحيات الخزينة
بيانات الخزينة وأرصدتها وحركاتها وتقاريرها متاحة لصاحب التطبيق فقط، ولا تظهر للموظفين.

### 9.2 الرصيد الافتتاحي
- إدخال الرصيد النقدي الموجود فعلياً مرة واحدة عند بدء استخدام التطبيق.
- لا يعتبر تحصيلاً أو إيراداً أو مصروفاً.
- لا يُطلب مرة أخرى بعد تسجيله.
- لا يقبل التعديل العادي؛ التصحيح لصاحب التطبيق فقط، مع السبب والقيم القديمة والجديدة والتاريخ والاحتفاظ بالأصل.

### 9.3 حركات الإيداع والسحب
- سبب الحركة إلزامي، والملاحظات اختيارية.
- تاريخ ووقت التسجيل تلقائيان.
- يمكن اختيار تاريخ حركة قديم عند الحاجة مع الاحتفاظ داخلياً بتاريخ التسجيل الحقيقي.
- عند اختيار تاريخ قديم يظهر تنبيه بسيط بالتاريخ المختار مع خيار المتابعة أو الرجوع.
- لكل حركة رقم مسلسل فريد مستقل مثل TR-000001، لا يتكرر ولا يتغير بالتعديل أو الإلغاء.
- البحث بالمبلغ أو السبب أو الملاحظات أو رقم الحركة أو رقم الطلب، وفتح الحركة من المستند المرفق.
- تصنيفات للإيداع والسحب قابلة للإضافة لاحقاً؛ السبب التفصيلي يظل إلزامياً.
- ربط اختياري بالطلب أو المصروف المرتبط، دون إنشاء تحصيل/مصروف جديد أو تكرار المبلغ.
- إرفاق صورة مستند/إيصال اختيارياً وعرضها بالتفاصيل والاحتفاظ بها مع السجل.
- سجل الحركات يدعم البحث والفلاتر حسب النوع والفترة، الأحدث أولاً، وفتح التفاصيل وسجل التعديلات.
- تعديل أو إلغاء الحركة لصاحب التطبيق فقط، مع القيم القديمة والجديدة وسبب التعديل/الإلغاء والتاريخ والوقت، والاحتفاظ بالسجل الأصلي.
- قبل تعديل/إلغاء حركة قديمة يظهر تنبيه يوضح تاريخها ونوعها ومبلغها وتأثيرها على أرصدة الأيام التالية ويطلب السبب والتأكيد.
- إعادة احتساب الأرصدة اللاحقة المتأثرة تلقائياً بعد التعديل أو الإلغاء، مع الاحتفاظ بالإقفالات الأصلية وسجل التصحيحات.
- منع السحب الذي يتجاوز الرصيد المتاح، ومنع أي عملية أو إلغاء يؤدي إلى رصيد سالب.
- التحقق الذري من الرصيد على مستوى قاعدة البيانات بحيث التحقق وتسجيل الحركة وتحديث الرصيد عملية واحدة آمنة ضد العمليات المتزامنة؛ تعطيل الزر وحده غير كافٍ.
- التحقق من المبالغ: منع الصفر والسالب والحروف/الرموز غير الصحيحة، قبول الكسور عند الحاجة، عرض الجنيه المصري، والتحقق قبل الحفظ وعلى مستوى قاعدة البيانات.
- طباعة/تصدير سجل الحركات PDF ومشاركته عبر واتساب مع الفترة والنوع وإجماليات الإيداع والسحب وصافي الحركة والتفاصيل والأسباب والملاحظات والرصيد قبل/بعد.

### 9.4 نظرة عامة ووسائل الدفع
تعرض نظرة عامة:
- رصيد الخزينة الحالي.
- إجمالي إيداعات اليوم.
- إجمالي سحوبات اليوم.
- إجمالي التحصيلات النقدية اليوم.
- إجمالي المصروفات النقدية اليوم.
- حالة إقفال اليوم.
- آخر خمس حركات.

يُعرض في ملخص واحد النقد الفعلي بالخزينة، والتحويلات البنكية، والمحافظ الإلكترونية، مع فصلها تماماً وعدم إدخال التحويلات والمحافظ في رصيد النقدية. يجب فصل التحصيلات والمصروفات عن الإيداعات والسحوبات لمنع احتساب المبلغ مرتين.

### 9.5 إقفال اليوم
- تسجيل رصيد بداية اليوم وحساب النقدية المتوقعة من الحركات النقدية.
- إدخال النقدية الفعلية وإظهار العجز أو الزيادة والملاحظات.
- الاحتفاظ بسجل الإقفال اليومي.
- ترحيل الرصيد الفعلي بعد الإقفال لليوم التالي؛ لا يرحّل الرصيد المتوقع إذا اختلف عن الفعلي.
- منع الإقفال مرتين.
- السماح بإقفال يوم حتى دون حركات مالية، مع تسجيل النقدية الفعلية وترحيلها.
- لا تنشأ إقفالات تلقائية أو افتراضية للأيام التي لم تُقفل؛ تظهر بحالة «لم يتم الإقفال»، ويستمر الرصيد من آخر إقفال فعلي. يمكن لصاحب التطبيق إجراء إقفال متأخر مع توضيح ذلك.
- تصحيح إقفال سابق لصاحب التطبيق فقط، بسبب وتاريخ ووقت، مع الاحتفاظ بالإقفال الأصلي.
- تنبيه العجز/الزيادة يعرض المبلغ الدقيق ويطلب ملاحظة؛ لا يسجل الفرق تلقائياً كإيراد أو مصروف.
- حفظ لقطة من إجماليات اليوم والرصيد والفرق بعد تأكيد الإقفال.
- أي تصحيح لاحق يرتبط بالإقفال الأصلي ولا يغيره بصمت.
- عند تسجيل إيداع أو سحب أو تحصيل أو مصروف نقدي بتاريخ يوم سبق إقفاله: تنبيه يوضح أن اليوم مقفل ويطلب تأكيد المتابعة؛ مع الاحتفاظ بالإقفال الأصلي وإعادة احتساب الأرصدة المتأثرة وتوثيق الأثر.
- التحقق من مبلغ النقدية الفعلية: منع السالب والقيم غير الصحيحة، قبول الكسور، توضيح الجنيه المصري.
- شاشة مراجعة مختصرة قبل التأكيد تعرض رصيد البداية والتحصيلات والمصروفات والإيداعات والسحوبات والنقدية الفعلية والعجز/الزيادة، مع الرجوع للتعديل أو تأكيد الإقفال.
- البحث في سجل الإقفالات حسب التاريخ، وفتح التفاصيل والتصحيحات المرتبطة.
- طباعة ومشاركة ملخص إقفال اليوم PDF من داخل تفاصيل الإقفال.
- تنبيه في الصفحة الرئيسية عند انتهاء اليوم دون إقفال الخزينة؛ الضغط عليه يفتح تبويبة إقفال اليوم.
- منع الإقفال إذا كانت حركة مالية غير مكتملة أو ما زالت قيد الحفظ، مع توضيح السبب.

### 9.6 معادلة الرصيد النقدي
الرصيد النقدي المتوقع = رصيد البداية + التحصيلات النقدية + الإيداعات − المصروفات النقدية − السحوبات.

- التحويلات البنكية والمحافظ الإلكترونية خارج هذه المعادلة.
- منع احتساب أي حركة مرتين.
- بعد الإقفال يصبح الرصيد الفعلي رصيد بداية اليوم التالي.

### 9.7 الربط مع التحصيلات والمصروفات
- التحصيل النقدي يزيد رصيد الخزينة مرة واحدة تلقائياً.
- المصروف النقدي يخفض رصيد الخزينة مرة واحدة تلقائياً.
- لا تنشأ حركات إيداع أو سحب إضافية بسبب التحصيل/المصروف.
- التحويل البنكي والمحفظة منفصلان.
- عند تعديل/إلغاء تحصيل أو مصروف نقدي يعاد احتساب أثره على الخزينة، مع سجل تغييرات ومنع الرصيد السالب.
- عند تسجيل تحصيل/مصروف نقدي بتاريخ يوم مقفل، تنبيه وتأكيد، مع الحفاظ على الإقفال وإعادة احتساب الأرصدة المتأثرة وتوثيق الأثر.
